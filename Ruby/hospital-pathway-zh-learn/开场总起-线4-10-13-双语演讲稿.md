## 4. 线 10｜自费完整路径（对着路线自己讲）

病例号 `DEMO-JAVA-01`。Java 要开着。重点：`request-payment`；可选失败支 `mark-payment-investigate`。

```
开始申请 / Start request
  → P1 登记　【选】新转诊 - 材料已核验 / New referral - documents checked
  → P2 转诊　【选】接受 / Accept
  → P3/P4 预约　【选】已预约、通知且已到诊 / Booked, notified and attended
       ← B：check-slot（自动）

  → 【终点】本段诊疗结束 / Care episode ended
```

成功日志：`request-payment SUCCESS ... publishing payment-result`，然后 `send-booking-confirmation SENT ...`  
失败（10.00）额外：`mark-payment-investigate case=... status=INVESTIGATE ...`

### 这条线上谁的 Worker

On this route the payment file is `HospitalPathwayWorkers.java`. The method is `requestPayment`, job type `request-payment`.

这条路上付款的文件是 `HospitalPathwayWorkers.java`。方法是 `requestPayment`，任务类型是 `request-payment`。

If the amount is `10.00`, my refund class also runs: `markPaymentInvestigate` in `RefundWorkers.java`, job type `mark-payment-investigate`. I will say that after the success path.

金额如果是 `10.00`，退款这个类里还有一个方法会跑：`RefundWorkers.java` 的 `markPaymentInvestigate`，任务类型是 `mark-payment-investigate`。成功路径讲完再提它。

### Worker 和 Message

A worker is a Java method that Camunda calls. On the diagram, the send task has a job type. That text must match `@JobWorker(type = "request-payment")`. When the token reaches that task, the engine hands the job to this method.

Worker 就是 Camunda 会来调用的一个 Java 方法。图上这个发送任务有一个任务类型。这段文字必须和 `@JobWorker(type = "request-payment")` 一致。令牌走到这一步，引擎就把作业交给这个方法。

A message is not the worker. The worker calls the outside payment service. The message brings the result back into the process. The diagram has two shapes here: the send task “send payment request”, then the catch “payment result received”. The catch is waiting. It moves on only when the message name is `payment-result`, and the correlation key is the case ID.

消息不是工作器。工作器负责去调外面的支付。消息负责把结果送回流程。图上这里是两个形状：发送任务「发出支付请求」，然后是捕获「收到支付结果」。捕获事件在等。只有消息名叫 `payment-result`，并且关联键是病例号，流程才会往下走。

The annotation says `autoComplete = false`. So this method must publish first, and complete the send task second. If we only complete the job and never publish, the token stays on the catch.

注解写了 `autoComplete = false`。所以这个方法必须先发布消息，再完成发送任务。如果只完成作业、不发消息，令牌会停在捕获事件上。

指代码：`HospitalPathwayWorkers.requestPayment`。发布在 `messageName("payment-result")` 和 `correlationKey(caseReference)`。

### `requestPayment` 里比较重要的四步

First, read the case ID from `case_reference` or `patientId`, and read `charge_amount`. No case ID: fail the job. Do not publish.

先读病例号，来自 `case_reference` 或 `patientId`，再读金额 `charge_amount`。没有病例号就让作业失败。不发消息。

Second, if `payment_requested_once` is already true, reuse the old status and the old reference, then complete. Do not publish again. That is how the demo avoids a second charge.

第二，如果 `payment_requested_once` 已经是 true，就复用上次的状态和流水号，然后完成。不再发消息。演示里这样就不会扣第二次。

Third, the demo rule: if the amount text ends with `0`, the status is unsuccessful. Otherwise it is successful, and the code makes a reference like `TX-xxxxxxxx`. So `10.01` succeeds and `10.00` fails. We never store a card number.

第三，演示规则：金额文字以 `0` 结尾就是失败，否则成功，并生成 `TX-` 开头的流水号。所以 `10.01` 成功，`10.00` 失败。不存卡号。

Fourth, `publishMessage`. The name is `payment-result`. The correlation key is the case ID. The message carries `payment_status`, `transaction_reference`, and `payment_date`. Only then does the method complete the send task, and set `payment_requested_once` to true.

第四，`publishMessage`。名字是 `payment-result`。关联键是病例号。消息里带 `payment_status`、`transaction_reference` 和 `payment_date`。这之后方法才完成发送任务，并把 `payment_requested_once` 设为 true。

On the fail branch the same payment worker still publishes `payment-result`, with status unsuccessful. After the catch, `RefundWorkers.markPaymentInvestigate` runs. That one is a normal service task. It does not publish a message. It writes one `payment_ledger` row as `INVESTIGATE`, and one audit row with actor `ruby`. A person then handles the funding issue. We do not charge again.

失败支上，同一个付款工作器仍会发布 `payment-result`，状态是 unsuccessful。捕获之后跑的是 `RefundWorkers.markPaymentInvestigate`。那是普通服务任务，不发消息。它在 `payment_ledger` 写一行 `INVESTIGATE`，并写一条审计，操作人是 `ruby`。然后由人处理经费问题。不会再扣一次。

## 5. 线 13｜变更后退款（对着路线自己讲）

病例号 `DEMO-001`。Java 要开着。表单后自动跑 `request-refund`，写 `payment_ledger`。

```
开始申请 / Start request
  → P1 登记　【选】授权变更 / 随访 / 取消 / Authorised change / follow-up / cancellation
  → P11/P12 变更　【选】授权停止 / 出院 - 需财务复核
                / Authorise stop / discharge - Finance review required
       ← D：notify-care-change（自动）
  → ★ P7 财务调整　form = finance_adjustment
       【选】财务决定已授权且结果已记录 / Financial decision authorised and outcome recorded
  → ★ Service Task「Request refund」← Java request-refund（写 payment_ledger SUCCESSFUL）
       ← 控制台：request-refund case=... decision=resolved status=SUCCESSFUL
  → 【终点】本段诊疗结束 / Care episode ended
```

若选「提供方结果待定 / pending」→ `request-refund` 写 INVESTIGATE，网关回到财务调整重试。

### 退款 Java（就是这个类）

Yes, the refund is route 13. The class is `RefundWorkers.java`. The method is `requestRefund`, job type `request-refund`. It runs by itself after the finance form. This step is not a message. The method returns a map, and Camunda completes the job.

对，退款就是线 13。类是 `RefundWorkers.java`。方法是 `requestRefund`，任务类型是 `request-refund`。财务表填完后它自动跑。这一步不是消息。方法返回一个 Map，Camunda 会完成这个作业。

It reads `financeAdjustment`. If the value is `resolved`, it writes `payment_ledger` as `SUCCESSFUL`, and returns `refund_status` `SUCCESSFUL`. Any other value, including pending, writes `INVESTIGATE`, and the gateway sends the token back to the finance form.

它读 `financeAdjustment`。如果是 `resolved`，就把 `payment_ledger` 写成 `SUCCESSFUL`，并返回 `refund_status` `SUCCESSFUL`。其他值，包括 pending，写成 `INVESTIGATE`，网关把令牌送回财务表。

The guard that matters is the idempotency key: case ID, the word refund, the decision, and the amount. The same retry does not insert a second row. It also appends `audit_event` with actor `ruby`.

比较重要的是幂等键：病例号、refund、决定、金额。同一次重试不会插入第二行。它还会追加 `audit_event`，操作人是 `ruby`。

指代码：`RefundWorkers.requestRefund`。`resolved` 对应 `SUCCESSFUL` 的判断，以及 `upsertLedger`。

## 6. 收尾

On route 10, `request-payment` must publish the message `payment-result`, or the process keeps waiting. On route 13, `RefundWorkers.requestRefund` only writes the ledger. Route 4 has no worker.

线 10 上，`request-payment` 必须发布消息 `payment-result`，否则流程会一直等。线 13 上，`RefundWorkers.requestRefund` 只写账本。线 4 没有工作器。
