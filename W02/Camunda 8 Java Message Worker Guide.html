Camunda 8 Java Message Worker Guide

A step-by-step guide to publishing a BPMN message from a Spring job worker and correlating it with a waiting message catch event. The example uses a fixed correlation value for teaching; a real process should normally use a shared business identifier.

Initialise the Process

Initialise all the corelation keys before running the process instance.

Go to modeler  Variables  Initialise all the corelation Keys

1 Configure the receiving process

Add an intermediate message catch event to the receiving process. In Camunda Modeler, define a message with the name Message01. Set its Subscription Correlation Key to a FEEL expression that reads a process variable:

Message name: Message01Subscription Correlation Key: <<correlationKey>>

2 Configure the sending task

Add a service task to the sending process. Set Task Definition Type to send-message-01. This value must match the worker annotation exactly:

@JobWorker(type = "send-message-01", autoComplete = false)

With autoComplete set to false, the method must complete or fail the activated job itself.

3 Register and inject the Camunda client

Annotate the class with @Component so Spring discovers it. Constructor injection gives the worker a CamundaClient for publishing the message and completing the job.

@Componentpublic class MessageHandeller { private final CamundaClient camundaClient; public MessageHandeller(CamundaClient camundaClient) { this.camundaClient = camundaClient; }}

4 Read variables and publish the message

The worker reads the variables visible to its job. In this teaching example, the published message name and correlation key both happen to be Message01, but they have separate purposes. The name identifies the message type; the key selects a matching receiving subscription.

Map<String, Object> variables = job.getVariablesAsMap();camundaClient.newPublishMessageCommand() .messageName("Message01") .correlationKey("Message01") .variables(variables) .timeToLive(Duration.ofMinutes(10)) .send() .join();

The variables are message payload. The 10 minute time to live allows Camunda to buffer the message if the receiving subscription is not yet open. The publish command succeeding means Camunda accepted publication; it does not prove that a process instance received the message. Check the receiving process in Operate to verify correlation.

5 Complete the sending job

Only after the publish command completes, complete the activated sending job. Its process can then continue.

camundaClient.newCompleteCommand(job.getKey()) .variables(variables) .send() .join();

6 Fail the job if an operation fails

On an exception, send a fail command with one fewer retry. When retries reach zero, Camunda raises an incident. In a deployed application, log the exception with your normal logger.

jobClient.newFailCommand(job) .retries(Math.max(job.getRetries() - 1, 0)) .errorMessage("Could not publish message: " + e.getMessage()) .send() .join();

If publication succeeds but completing the job fails, a retry may publish the same message again. For production use, design for duplicate attempts, for example with a stable message ID and appropriate idempotency.
